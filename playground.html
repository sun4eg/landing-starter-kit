Usage guidance

  • Choose the component based on content responsibility, not surface appearance.
  • Use semantic headings that fit the surrounding document hierarchy.
  • Write descriptive link text instead of making the entire card interactive.
  • Do not make non-interactive card areas appear clickable.
  • Use meaningful imagery with accurate alternative text.
  • Let content determine card height instead of imposing fixed dimensions.

The Service Card link may be omitted without an empty wrapper. Text length remains intrinsic in both components. Project media keeps its wrapper; replace only the placeholder when approved media exists.

Accordion

Review the accessible disclosure structure, single-open and multiple-open configuration, progressive enhancement contract, and resilient content behavior.

Default single-open Accordion

The first item opens after enhancement, and opening another item closes the previously open panel.

The trigger uses flexible layout, the label can wrap, and the icon remains a fixed-size decorative element. The panel has no fixed height, so its content grows naturally.

Multi-paragraph answers remain ordinary document content. For related context, continue to the Accordion accessibility guidance.

The previously open item closes because single-open behavior is the default.

Yes. Activating the open trigger collapses its panel without forcing another item open.

No. The existing component changes visibility with the native hidden attribute.

Multiple-open Accordion

This independent instance allows several panels to remain open when configured with data-accordion-multiple="true".

Yes. Open another item and this panel remains visible until it is closed directly.

No. Each Accordion owns its own items, listeners, and configuration.

The first item opens after enhancement; other items can then be opened independently.

Progressive enhancement

Without JavaScript

All answers are visible and semantically readable. Triggers remain disabled, so fallback controls are not presented as broken interactive buttons.

With JavaScript

Valid instances become interactive, aria-expanded stays synchronized with hidden, the first item opens initially, and multiple-open behavior follows its data configuration.

State ownership

  • aria-expanded communicates trigger state.
  • hidden controls panel visibility.
  • Data attributes provide JavaScript behavior hooks; styling classes are not queried.
  • data-accordion-enhanced is implementation-owned and is not public authoring API.

Interaction and accessibility guidance

  • Native buttons provide Enter and Space activation; custom arrow-key behavior is unnecessary.
  • Visible focus is inherited from the global focus-visible system.
  • Closing a panel that contains focus returns focus to its trigger.
  • Use question headings at the level required by the surrounding document.
  • Keep essential content readable in the unenhanced fallback.
  • Avoid nested Accordions unless the project explicitly defines their behavior.

Required relationships

Group each trigger and panel in one item; the trigger ID labels the panel, and aria-controls points back to that panel ID. 

<div class="accordion" data-accordion>
  <article class="accordion__item" data-accordion-item>
    <h4 class="accordion__heading">
      <button id="question-1" aria-expanded="true"
        aria-controls="answer-1" data-accordion-trigger disabled>...</button>
    </h4>
    <div id="answer-1" aria-labelledby="question-1"
      data-accordion-panel>...</div>
  </article>
</div>

Forms

Review floating-label fields, native validation, semantic HTML requirements, Button composition, and resilient form content without a custom submission layer.

Complete form and native validation

Submit with required fields empty to inspect browser-native validation; exact prompts vary by browser, and this Playground has no submission backend.

This form posts only to the current Playground URL. Do not enter personal or sensitive information.

Inspect floating-label states

Use the complete form above to inspect real browser states without permanent simulation classes.

  1. Start with an empty field: its label rests inside the control.
  2. Focus the field: the label moves onto the outlined border.
  3. Enter a value and blur: the label remains raised.
  4. Delete the value and blur: the label returns inside the control.
  5. Use saved browser data to inspect autofill; no fake autofill state is provided.
  6. Submit with required fields empty or an invalid email to inspect native validation.

Required and optional fields

  • Use the native required attribute only when the field is necessary.
  • Identify optional fields in visible copy when their status may be ambiguous.
  • Do not communicate required state through color alone.
  • Label position depends on focus or content, not validity.
  • Validation state and floating-label state are separate responsibilities.

Button composition

Form owns field and action layout. Button remains an independent component composed inside .form__actions; Form does not override Button internals.

The live example uses the existing primary and full-width Button APIs within the constrained form.

Accessibility guidance

  • Provide a real label for every control; placeholder-only labels are prohibited.
  • Keep every for/id relationship unique.
  • Match autocomplete values and native input types to each field’s purpose.
  • Use native required state and retain browser validation.
  • Keep logical DOM order because it defines keyboard tab order.
  • Visible focus is inherited from the global focus-visible system.
  • Use disabled fields carefully; this component has no intentional disabled visual API.
  • Custom submission errors and status updates require an accessible messaging strategy.

Floating-label field structure

The control must precede its label for the sibling selector, and the single-space placeholder is the CSS state hook rather than visible instructional copy. 

<div class="form__field">
  <input class="form__input" id="name" name="name"
    type="text" placeholder=" " autocomplete="name" required />
  <label class="form__label" for="name">Name (required)</label>
</div>

Required HTML contract

Preserve these relationships so floating labels and native semantics remain reliable.

  • Wrap each control and label with .form__field.
  • Place the control immediately before its label.
  • Include placeholder=" " as the CSS state hook.
  • Match the control ID to the label’s for.
  • Choose the appropriate native type and autocomplete value.
  • Add required only when semantically necessary.

Progressive enhancement

Without JavaScript

Navigation remains visible, links remain usable, and the hidden toggle is not exposed as a broken control.

With JavaScript

Valid roots are enhanced, the toggle becomes available, and aria-expanded, its label, and the root’s runtime open state stay synchronized. The collapsed menu removes its links from the focus order; Escape and menu-link activation close it.

Responsive ownership

  • Desktop presentation appears above the shared tablet breakpoint.
  • At and below that breakpoint, CSS exposes the toggle and collapsible menu for enhanced roots.
  • JavaScript does not duplicate Sass breakpoint values.
  • Viewport changes leave no conflicting inline display state because visibility remains CSS-owned.

Architecture boundaries

  • .site-header is the page-wide structural Header block.
  • .primary-navigation is the reusable navigation presentation block.
  • Header composition elements place the logo, navigation, toggle, contact, and actions.
  • Behavior hooks use data attributes rather than BEM styling classes.

State ownership

  • aria-expanded communicates the toggle’s semantic state.
  • The Navigation module owns the root’s runtime open state.
  • Responsive visibility belongs to CSS, not JavaScript.
  • Sticky and scrolled Header states belong to the separate Sticky Header module.
  • Runtime enhancement attributes are implementation details, not authoring API.

Interaction guidance

  • Use links for destinations and a button only for opening and closing the menu.
  • Native Enter and Space activate the toggle.
  • Escape closes an open menu and restores focus to its toggle.
  • Following a menu link closes that instance’s menu.
  • Write navigation labels that remain understandable out of context.
  • Keep essential destinations available without JavaScript.
  • Give multiple navigation landmarks distinct accessible labels.

Responsive markup contract

Scope one toggle and menu to each root, and make the toggle’s aria-controls match that menu’s unique ID. 

<header class="site-header" data-navigation>
  <button aria-expanded="false" aria-controls="menu-1"
    data-navigation-toggle hidden>Menu</button>
  <nav class="primary-navigation" id="menu-1"
    aria-label="Primary navigation" data-navigation-menu>
    <ul class="primary-navigation__list">
      <li class="primary-navigation__item">
        <a class="primary-navigation__link" href="#navigation-title">Navigation</a>
      </li>
    </ul>
  </nav>
</header>

Brand and responsive behavior

The page Footer below demonstrates a short brand; the isolated preview above deliberately exercises a longer name, multi-line description, long labels, and a long email address.

Layout progression

The existing shared breakpoints move the top area from multiple columns through a reduced-column composition to a single mobile stack. The compact lower row wraps and then stacks naturally.

Intrinsic content

Brand copy, links, contact values, and legal labels wrap without fixed heights. Source order remains the reading and focus order as the visual layout changes.

Optional content

Optional regions are omitted with their wrappers so the Footer retains natural height and does not expose empty groups.

  • The production Footer composes no CTA, so this preview does not invent one.
  • Legal navigation is optional; omit its complete landmark when published policy destinations do not exist. The preview links lead to local documentation, not fictional policy pages.
  • Fewer navigation links remain a valid intrinsic list and require no empty items.
  • Long contact values wrap, and Footer regions grow with their content rather than fixed heights.

Contact semantics

Reserve <address> for contact details associated with the Footer owner.

  • Use tel: for phone numbers and mailto: for email addresses.
  • Keep a physical address as text unless a real linked destination is available.
  • Do not place unrelated organization descriptions or legal copy inside <address>.

Usage guidance

Keep the Footer concise, semantic, and aligned with real site destinations.

  • Keep link groups purposeful and give multiple navigation landmarks distinct accessible labels.
  • Use meaningful link text, real contact links, and published legal destinations.
  • Keep descriptions concise and do not force columns to equal heights.
  • Preserve logical source order and sufficient text and focus-indicator contrast.
  • Maintain the copyright year manually or adopt an intentional dynamic strategy elsewhere.
  • Keep visual and source order aligned; the Footer should not become a component showcase.
