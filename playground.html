Role and live-region ownership

Static Alerts need no role and are read in document order. A runtime may add role="alert" for a genuinely urgent dynamically inserted error or role="status" for a non-urgent dynamic update. Visual tone does not determine the role, and the base component adds no live region.

Enhancement and focus

Valid dismissible instances reveal their authored button after initialization. Dismissal immediately removes the in-flow message without animation. Keyboard dismissal moves focus to the next visible focusable element in document order, with the previous visible control as a fallback. Pointer dismissal does not force focus movement.

Usage and accessibility guidance

  • Use Alert for contextual information that belongs within the current page flow.
  • Use the future Toast for transient global feedback and the future Modal for blocking decisions.
  • Use Badge for compact labels; do not use Alert as an individual form-field error.
  • Choose live-region roles from runtime urgency, never from the visual variant alone.
  • Keep actions limited, descriptive, and semantically correct.
  • Make decorative icons hidden from assistive technology and keep all meaning in visible text.
  • Use dismissal only when removing the message does not remove information the user still needs.

Semantic strategy

The required track and bar API cannot be authored as children of native <progress> consistently across browsers. Therefore the visible track uses role="progressbar" with synchronized minimum, maximum, current value, and accessible naming. The component remains non-interactive.

State ownership

--progress-value controls only visual fill and must be a percentage from 0% to 100%. It is component-scoped state, not a global design token. Authors must keep it synchronized with the matching numeric aria-valuenow value from 0 to 100; CSS does not derive ARIA state. This static component adds no animation, polling, or JavaScript state.

Usage and accessibility guidance

  • Use Progress only when the completed proportion is known and measurable.
  • Use Spinner for unknown-duration activity and Skeleton for loading content structure.
  • Use Range or Number Stepper when the user controls a value; Progress is not interactive.
  • Use Timeline for ordered events rather than a numeric completion amount.
  • Give every progressbar an accessible name through aria-labelledby or aria-label.
  • Keep visual fill and aria-valuenow synchronized.
  • Do not rely on semantic color without visible status wording.

Motion behavior

The visual uses one continuous rotation during normal operation. Under prefers-reduced-motion: reduce, rotation stops and the ring becomes complete and static; the authored status text remains the source of meaning.

Status semantics

Apply role="status" when a loading message should be announced politely. Do not add a second aria-live. When appropriate, aria-busy="true" belongs on the region being updated rather than on Spinner itself.

Usage and accessibility guidance

  • Use Spinner for short waits whose completion percentage is unknown.
  • Use Progress for measurable completion and Skeleton for loading page-content structure.
  • Use Alert or a future Toast for outcome messages; Spinner communicates activity, not success or failure.
  • Prefer concise visible text for consequential or longer waits.
  • Use visual-only Spinner sparingly and always provide its status container an accessible name.
  • Avoid several simultaneous status regions because repeated announcements can become noisy.
  • Remove Spinner or update its status message when loading completes.
  • Do not use Spinner as decorative motion, a success or failure state, or an automatic page blocker.

Accessibility ownership

Skeleton shapes are decorative and use aria-hidden="true". When useful, aria-busy="true" belongs on the surrounding region being updated. Provide separate status text when users need a loading announcement; do not put roles or labels on individual shapes.

Motion behavior

A token-timed surface shimmer provides subtle activity without implying completion. Under prefers-reduced-motion: reduce, the shimmer layer is removed and the static shapes remain.

Usage and accessibility guidance

  • Match the approximate structure of the incoming content without reproducing every detail.
  • Use Spinner for compact indeterminate activity and Progress for measurable completion.
  • Do not use Skeleton as a permanent placeholder, progress measure, or decorative animation.
  • Keep loading regions understandable and replace Skeleton promptly with real content.
  • Avoid excessive shapes that create visual noise or make layout shifts more likely.
  • Hide every Skeleton shape from assistive technology and place busy state on the updated region.

Typography usage guidance

Start from meaning, then apply the smallest appropriate presentation API.

  • Choose the semantic element and correct heading level before considering visual size.
  • Keep exactly one page-level <h1> and never skip levels for visual reasons.
  • Use Text for reusable content composition and keep modifiers paired with .text.
  • Use readable measure for sustained copy, not every label or control.
  • Keep headings concise and use design tokens instead of hardcoded sizes or line heights.
  • Do not use visual scale to imply document structure.

Progressive enhancement

Without JavaScript

Navigation remains visible, links remain usable, and the hidden toggle is not exposed as a broken control.

With JavaScript

Valid roots are enhanced, the toggle becomes available, and aria-expanded, its label, and the root’s runtime open state stay synchronized. The collapsed menu removes its links from the focus order; Escape and menu-link activation close it.

Responsive ownership

  • Desktop presentation appears above the shared tablet breakpoint.
  • At and below that breakpoint, CSS exposes the toggle and collapsible menu for enhanced roots.
  • JavaScript does not duplicate Sass breakpoint values.
  • Viewport changes leave no conflicting inline display state because visibility remains CSS-owned.

Architecture boundaries

  • .site-header is the page-wide structural Header block.
  • .primary-navigation is the reusable navigation presentation block.
  • Header composition elements place the logo, navigation, toggle, contact, and actions.
  • Behavior hooks use data attributes rather than BEM styling classes.

State ownership

  • aria-expanded communicates the toggle’s semantic state.
  • The Navigation module owns the root’s runtime open state.
  • Responsive visibility belongs to CSS, not JavaScript.
  • Sticky and scrolled Header states belong to the separate Sticky Header module.
  • Runtime enhancement attributes are implementation details, not authoring API.

Interaction guidance

  • Use links for destinations and a button only for opening and closing the menu.
  • Native Enter and Space activate the toggle.
  • Escape closes an open menu and restores focus to its toggle.
  • Following a menu link closes that instance’s menu.
  • Write navigation labels that remain understandable out of context.
  • Keep essential destinations available without JavaScript.
  • Give multiple navigation landmarks distinct accessible labels.

Responsive markup contract

Scope one toggle and menu to each root, and make the toggle’s aria-controls match that menu’s unique ID.

Token model

Dependencies flow from component-local decisions through semantic purposes to primitive foundations.

1. Primitive

Raw palette, spacing, type, radius, shadow, motion, and layer values.

2. Semantic

Purpose-led tokens such as text, surface, focus, control, measure, and sticky concepts. Reusable components should prefer this layer.

3. Component-local

Scoped mappings such as Button’s --button-background and --button-height. They support component variants but are not global authoring tokens.

Sass breakpoints

Breakpoints are compile-time Sass variables, not CSS custom properties.

$mobile: 40rem

Shared transition for mobile single-column and touch-friendly compositions.

$tablet: 64rem

Shared transition for tablet and reduced-column compositions.

Components consume these shared Sass variables. JavaScript must not duplicate their numeric values.

Z-index layers

The ordered semantic scale replaces raw stacking values.

  1. --z-baseBase content · active
  2. --z-raisedDecorative or raised content · active
  3. --z-dropdownDocumentation panel layer · active

  5. --z-overlayOverlay layer · reserved
  6. --z-modalModal layer · reserved
  7. --z-toastTop utility layer and Skip link · active

Decorative layers stay below controls, and the Skip link remains above the sticky Header through --z-toast.

Usage guidance

Preserve the intent encoded by the existing system.

  • Prefer semantic tokens over primitives inside reusable components.
  • Add a token only for a demonstrated reusable concept; do not alias every primitive.
  • Avoid raw visual values and keep component-local custom properties scoped.
  • Use shared Sass breakpoints plus semantic z-index and sticky tokens.
  • Preserve accessibility intent in color relationships, focus, reduced motion, control sizing, and readable measure.
  • Review real foreground/background combinations rather than assuming a token guarantees contrast.
