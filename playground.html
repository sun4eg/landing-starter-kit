Role and live-region ownership

Static Alerts need no role and are read in document order. A runtime may add role="alert" for a genuinely urgent dynamically inserted error or role="status" for a non-urgent dynamic update. Visual tone does not determine the role, and the base component adds no live region.

Enhancement and focus

Valid dismissible instances reveal their authored button after initialization. Dismissal immediately removes the in-flow message without animation. Keyboard dismissal moves focus to the next visible focusable element in document order, with the previous visible control as a fallback. Pointer dismissal does not force focus movement.

Usage and accessibility guidance

  • Use Alert for contextual information that belongs within the current page flow.
  • Use the future Toast for transient global feedback and the future Modal for blocking decisions.
  • Use Badge for compact labels; do not use Alert as an individual form-field error.
  • Choose live-region roles from runtime urgency, never from the visual variant alone.
  • Keep actions limited, descriptive, and semantically correct.
  • Make decorative icons hidden from assistive technology and keep all meaning in visible text.
  • Use dismissal only when removing the message does not remove information the user still needs.

Semantic strategy

The required track and bar API cannot be authored as children of native <progress> consistently across browsers. Therefore the visible track uses role="progressbar" with synchronized minimum, maximum, current value, and accessible naming. The component remains non-interactive.

State ownership

--progress-value controls only visual fill and must be a percentage from 0% to 100%. It is component-scoped state, not a global design token. Authors must keep it synchronized with the matching numeric aria-valuenow value from 0 to 100; CSS does not derive ARIA state. This static component adds no animation, polling, or JavaScript state.

Usage and accessibility guidance

  • Use Progress only when the completed proportion is known and measurable.
  • Use Spinner for unknown-duration activity and Skeleton for loading content structure.
  • Use Range or Number Stepper when the user controls a value; Progress is not interactive.
  • Use Timeline for ordered events rather than a numeric completion amount.
  • Give every progressbar an accessible name through aria-labelledby or aria-label.
  • Keep visual fill and aria-valuenow synchronized.
  • Do not rely on semantic color without visible status wording.

Accessibility ownership

Skeleton shapes are decorative and use aria-hidden="true". When useful, aria-busy="true" belongs on the surrounding region being updated. Provide separate status text when users need a loading announcement; do not put roles or labels on individual shapes.

  • Keep loading regions understandable and replace Skeleton promptly with real content.
  • Avoid excessive shapes that create visual noise or make layout shifts more likely.
  • Hide every Skeleton shape from assistive technology and place busy state on the updated region.

Loading boundary

Show Skeleton while expected content structure loads, Spinner for compact indeterminate activity, and Progress for measurable completion. Render Empty State only after loading completes and the result is genuinely empty; do not flash it while a request is pending.

Error boundary

Alert communicates contextual recoverable messages. Empty State is appropriate only when the region truly has no content to show; technical failures need clear recovery guidance and should not automatically be relabelled as empty content.

Usage and accessibility guidance

  • Explain what belongs in the region and why no content is currently shown.
  • Distinguish a genuinely empty collection from results excluded by a query or filter.
  • Offer a focused next step only when the user can meaningfully change the state.
  • Avoid generic messages such as “Nothing here” without useful context.
  • Limit prominent actions and use Button or link semantics according to the action.
  • Keep decorative visuals hidden and let visible text communicate the state.
  • Dynamic replacement may need application-level focus or status management; this component adds none.

Progressive enhancement

Authored tab buttons start disabled and all panels remain visible. A complete valid instance is then enabled, normalized to one selection, and reduced to one visible panel. Malformed instances remain static and readable rather than hiding content.

Focus and panel behavior

One enabled tab participates in sequential focus. Arrow keys move the roving target, but activation never forces focus into a panel. Inactive panels use hidden, so their descendants leave the focus order.

Usage and accessibility guidance

  • Use Accordion when several sections should remain independently expandable or comparable.
  • Use controls such as Radio or Switch for choices and toggles; Tabs are not segmented controls.
  • Prefer automatic activation when panels update immediately and manual activation for expensive work.
  • Keep the tab count reasonable and labels concise and descriptive.
  • This initial API does not synchronize URLs, browser history, or deep links.
  • Nested Tabs are intentionally unsupported; use a clearer content hierarchy instead.

Usage guidance

  • Use Checkbox for independent selections and Radio for one choice from a named group.
  • Use Switch only when changing it applies a binary setting immediately.
  • Do not use Switch when submission or confirmation is still required.
  • Use Select for one choice from a longer predefined list; prefer Radio when a small set should remain visible.
  • Give every Select a visible label, keep options concise, and use optgroup only for meaningful grouping.
  • Keep native Select behavior and never use its placeholder option as a replacement for a label.
  • Always label Password Inputs visibly and choose current-password or new-password autocomplete according to purpose.
  • Treat password visibility as optional enhancement; do not block paste or disable password managers.
  • Do not impose arbitrary password composition rules without explicit product and security requirements.
  • Use password fields only for secret content and plan accessible messages before adding custom validation.
  • Use Number Stepper for bounded quantities while preserving direct typing, deletion, paste, and native validation.
  • Prefer a plain number input when step buttons add little value, and use Select or Radio for small enumerated choices.
  • Keep min, max, and step meaningful; decimal steps remain supported.
  • Do not use Number Stepper for phone numbers, postal codes, identifiers, or card numbers.
  • Use Range Slider when approximate adjustment matters more than exact typing; use Number Stepper for precise entry.
  • Use Select or Radio for discrete named choices rather than presenting them as a numeric continuum.
  • Always label Range Sliders visibly and show the current value when feedback helps users decide.
  • Provide meaningful range boundaries and steps, avoid excessive precision, and preserve native keyboard behavior.
  • Do not hide critical values exclusively behind a Range Slider.
  • Use Date Picker for complete calendar dates and always provide a visible associated label.
  • Identify optional dates in visible copy and use native required, min, and max only when meaningful.
  • Expect the native date picker and displayed date order to vary across browsers, operating systems, and locales.
  • Use a different control when users need partial dates, date ranges, or date-and-time input.
  • Use Time Picker for a time of day, provide a visible label, and explain the relevant time zone or local-time context.
  • Use native min, max, and step constraints only when the permitted schedule requires them.
  • Expect time presentation and picker interaction to follow the user’s browser, operating system, and locale.
  • Use a different control for durations, time ranges, or scheduling rules that a single native time value cannot express.
  • Use DateTime Local only when one combined local date and time is required, and always explain its scheduling context.
  • Define meaningful native boundaries and intervals without treating the value as a time-zone-aware instant.
  • Establish time-zone handling separately when the same event must be understood across locations.
  • Use separate controls when independent date or time selection better matches the task.
  • Give every File Input a visible label and explain genuinely supported file types in visible text.

Usage guidance

Preserve the intent encoded by the existing system.

  • Prefer semantic tokens over primitives inside reusable components.
  • Add a token only for a demonstrated reusable concept; do not alias every primitive.
  • Avoid raw visual values and keep component-local custom properties scoped.
  • Use shared Sass breakpoints plus semantic z-index and sticky tokens.
  • Preserve accessibility intent in color relationships, focus, reduced motion, control sizing, and readable measure.
  • Review real foreground/background combinations rather than assuming a token guarantees contrast.
